## Phase S2-C1 — Auth + RLS Security Foundation

The first authorization slice is now defined for the five core identity/tenancy tables. Roles are trusted only from `school_memberships`, RLS helpers live in a non-exposed `private` schema, future Auth users receive a public profile via trigger, and browser membership writes remain forbidden. The other 21 domain tables stay closed until S2-C2. Runtime remains FastAPI/SQLite. See `SUPABASE_SECURITY_FOUNDATION_AR.md`.

## Phase S2-B5 Fix 1 — updated_at wall clock

The live S2-B5 acceptance exposed statement-scoped timestamp semantics. A follow-up migration replaces only the trigger helper with `clock_timestamp()`; all 22 existing triggers are reused.

## Phase S2-B5 — Final Schema Closure

The frozen PostgreSQL target is now closed at 26/26 tables and 299 columns. S2-B5 adds database-managed `updated_at` triggers to 22 tables, three final indexes, and whole-schema acceptance guards. Runtime remains FastAPI/SQLite; Auth/RLS policy work begins in S2-C. See `SUPABASE_SCHEMA_CLOSURE_AR.md`.

## Phase S2-B4 — Events / Documents / Requests / Activities

PostgreSQL now includes the seven remaining frozen target tables: `school_settings`, `upload_requests`, `documents`, `events`, `event_media`, `event_teacher_links`, and `activities`. Legacy year-link/meta tables are folded into the normalized target instead of being recreated. Runtime remains FastAPI/SQLite; no application data or storage bytes move yet.

## Phase S2-B3 — Operational domains migration

PostgreSQL now has a third versioned migration for meetings, curriculum planning, supervision, and achievement: 11 new operational tables with same-school composite foreign keys and academic-year isolation. Browser roles remain denied and runtime remains FastAPI/SQLite until later parity gates.

## Phase S2-B2 — Teachers domain migration

PostgreSQL now has a second versioned migration for the teacher domain: `teachers`, `teacher_profiles`, `teacher_years`, and `teacher_cv_items`. The deferred `school_memberships.teacher_id` link is completed with a same-school composite foreign key. Runtime remains FastAPI/SQLite and RLS remains deferred to S2-C.

### معنى «الاستمرارية الطولية»

وجود بيانات عدة سنوات يسمح بعرض التاريخ، البحث فيه، بناء التقارير السنوية، ومواصلة السجل المؤسسي. **ولا يعني ذلك تلقائيًا أن مقارنة مؤشر تربوي بين عامين صحيحة علميًا.** أي مقارنة تربوية مثل الإتقان أو انتشار الإتقان أو أثر تدخل بين سنوات مختلفة يجب أن تتحقق أولًا من توافق المرجع، والأداة، وطريقة الحساب، والمعيار العُماني المستخدم في كل سنة. لا ينشئ المرصد تكافؤًا تربويًا من تلقاء نفسه. كما لا يجمع التطبيق داخل السنة نفسها نسب الفئة المحققة للحد إذا اختلف الحد أو مصدره أو إصدار المرجع بين التقويمات؛ تظهر النتيجة حينها «غير مجمعة» بدل إنتاج متوسط أو نسبة مضللة.

التحقق من العام والتاريخ في v0.13 بنيوي فقط: يتأكد النظام أن تاريخ السجل يقع في إحدى السنتين الميلاديتين المكوّنتين للعام الدراسي، ولا يفترض من عنده حدود بداية أو نهاية الفصل الدراسي العُماني.

**v0.13.0 لا يحتاج Secret جديدًا ولا SQL يدويًا ولا يغير OAuth. ترقية SQLite إضافية ومحافظة على البيانات السابقة.**

## دورة التدخل وقياس الأثر في v0.12.0

يوسع هذا الإصدار التدخلات العلاجية والإثرائية الموجودة أصلًا داخل **التحصيل والنتائج** بدل إنشاء قسم موازٍ. لكل إجراء يمكن تسجيل مقياس أثر منظم يتضمن اسم المؤشر، الوحدة، اتجاه التحسن، خط الأساس، الهدف المسجل، النتيجة الفعلية، تاريخ القياس، ومصدر الهدف أو المعيار.

- المعادلات الحسابية لا تتحول إلى أحكام تربوية معيارية إلا إذا كان المعيار موثقًا في المصدر المسجل.

achievement_action_metrics

ويضاف عقد قياس الأثر إلى مسارات التدخل الحالية عبر `PUT` و`DELETE` لمقياس الإجراء. تظهر القياسات في تفاصيل التحصيل، «يحتاج انتباهك»، التقارير الرسمية، الأرشيف، والبحث الشامل.

**v0.12.0 لا يحتاج Secret جديدًا ولا يغير Google Drive أو GitHub Workflow. ترقية SQLite تتم تلقائيًا بإضافة الجداول الجديدة فقط، ولا يلزم SQL يدوي.**

يدعم التطبيع العربي اختلاف الهمزات والتشكيل والتطويل، ويبدأ الاستعلام بعد حرفين على الأقل. كما يمكن تصفية النتائج حسب القسم والعام الدراسي، وفتح البحث بسرعة عبر `Ctrl/Cmd + K`. نتائج الوحدات والقرارات والتدخلات وإجراءات المتابعة تشير إلى السجل الأب الصحيح حتى ينتقل المستخدم إلى موضع العمل الفعلي بدل صفحة بحث منفصلة.

لا يفهرس البحث نصوص التقارير المولدة لأنها ناتج مشتق وليست مصدر حقيقة. **v0.11.0 لا يضيف SQL أو Secret جديدًا ولا يغير إعداد Google Drive.**

## مركز التقارير الرسمي في v0.9.0

- التقرير الشامل لأعمال القسم.
- التقرير المهني للمعلم.
- تقرير التخطيط ومتابعة المنهج.
- تقرير التحصيل والنتائج.
- تقرير الإشراف الفني والزيارات.
- تقرير الاجتماعات والقرارات.

كل تقرير يحمل نطاق العام الدراسي والفصل، ومؤشرات محسوبة من السجلات الأصلية، وأقسامًا جدولية قابلة للطباعة على A4. مسار الخادم `/api/reports/official` للقراءة فقط ولا ينشئ جداول جديدة ولا يغير بيانات العمل. في GitHub Pages يستخدم مركز التقارير بيانات المعاينة نفسها بعقد مطابق، ولذلك يمكن فحص الشكل قبل تشغيل الخادم الفعلي.

**مبدأ مهم:** التقرير لا يعيد اختراع التحليل ولا يخلق أرقامًا موازية. فإذا كانت البيانات غير موجودة تظهر كغياب بيانات بدل ملئها بتخمينات أنيقة، وهي عادة بشرية مؤسفة في بعض التقارير.

يضيف الإصدار الحالي سجلًا منظمًا للتقويمات والنتائج يتضمن:

## البنية التقنية

- **Frontend:** React 19 + TypeScript + Vite، بواجهة عربية RTL.
- **Backend:** FastAPI.
- **Database:** SQLite مع تفعيل Foreign Keys وWAL.
- **File storage:** تخزين محلي للتطوير، أو Google Drive عبر OAuth ونطاق `drive.file`.
- **CI/CD:** GitHub Actions لاختبار الواجهة والخادم وبناء المعاينة.
- **Live preview:** GitHub Pages في وضع معاينة آمن ببيانات نموذجية؛ عمليات الحفظ والرفع الفعلية تحتاج خادم FastAPI.

## سياسة التخزين

- Google Drive يحفظ **الملفات الفعلية** عند تفعيل الربط.
- SQLite يحفظ **البيانات الوصفية والعلاقات وحالات سير العمل**.
- مفاتيح Google لا توضع في الواجهة الأمامية.
- OAuth refresh token يحفظ مشفرًا عند إعداد `APP_ENCRYPTION_KEY`.
- روابط الرفع الخارجية تستخدم token عشوائيًا، بينما تحفظ قاعدة البيانات hash فقط.

## الاختبارات والجودة

المستودع يستخدم GitHub Actions في كل رفع إلى `main` للتحقق من:

1. تثبيت تبعيات الواجهة.

3. تثبيت تبعيات الخادم والاختبار.

تُعامل نتيجة Actions الخضراء كنقطة قبول للإصدار المرفوع، ولا يُعتمد الإصدار كمرجع مستقر لمجرد نجاح تعديل محلي.

## منهج التطوير

- **GitHub هو مصدر الحقيقة للكود.**
- التطوير يتم على مراحل صغيرة ذات نطاق واضح.
- كل مرحلة تُبنى فوق آخر نقطة استقرار خضراء.
- ترقيات SQLite إضافية ومحافظة على البيانات القديمة ما لم توجد خطة ترحيل صريحة.
- لا تُكسر العقود السابقة لإضافة وحدة جديدة.
- قبل تسليم أي حزمة تُفحص كـOverlay فوق النسخة الحالية وتُعاد اختبارات القبول من الناتج نفسه.
- المعاينة الحية تبقى قابلة للمتابعة مع كل مرحلة.

## ما هو قادم

بعد إغلاق اختبار Railway الحي في v0.14-B، تأتي مرحلة **لوحة الاستمرارية والمقارنة المنضبطة عبر السنوات** ثم التكامل مع أدوات التحليل التعليمية. لا تُجرى مقارنة تربوية معيارية بين سنوات مختلفة إلا عند توافق المرجع والأداة وطريقة الحساب.

### S2-B5 Fix 1 — updated_at clock semantics
Live Supabase acceptance exposed that `statement_timestamp()` remains constant for an entire SQL statement. Version 0.21.1 adds a corrective migration that replaces only `public.set_row_updated_at()` with `clock_timestamp()` while preserving the already-applied S2-B5 migration and all 22 triggers.
